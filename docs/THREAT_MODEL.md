# Threat Model and Non-Goals

## Protected assets

The runtime is designed to protect repository scope, authority boundaries, trusted evidence, apply state, rollback state, and delivery receipts from accidental or model-generated misuse.

## Trust boundaries

- Model providers are untrusted producers of proposals and mutations.
- Repository paths, allowlists, forbidden paths, policy, authority, and acceptance criteria are trusted local inputs.
- Deterministic verifier results and locally computed hashes are trusted only when generated by the current runtime version.
- Apply executors are privileged boundaries and must validate their own receipts.
- External Git hosting, CI systems, and provider APIs are outside the runtime trust boundary.

## Covered threats

The current prototype includes controls for:

- path traversal, aliases, absolute paths, encoded separators, and symlink traversal;
- touched-file and patch-claim mismatch;
- changes outside an explicit allowlist or inside a forbidden list;
- missing authority, policy, context, or acceptance contracts;
- malformed provider output and unsupported contract values;
- stale or tampered hashes, receipts, handoffs, and registry records;
- unsafe patch markers, failed validation, apply failure, and recovery routing;
- uncontrolled repository writes before deterministic approval.

## Residual risks

The runtime does not prove that an approved patch is semantically correct, secure, performant, maintainable, or free of hidden behavior. String-based unsafe-content rules are intentionally incomplete. A malicious dependency, compromised host, compromised CI runner, incorrect allowlist, unsafe apply adapter, or vulnerable model provider can still cause harm.

Repository owners must run normal code review, tests, dependency review, secret scanning, static analysis, sandboxing, and least-privilege controls around this runtime.

## Non-goals

The current prototype does not provide:

- a security guarantee or complete vulnerability detector;
- autonomous production deployment;
- unrestricted shell, network, or repository authority;
- distributed consensus or multi-host durability;
- hosted enterprise identity, billing, dashboards, or compliance certification;
- proof that bounded or diffusion-style agents outperform other systems;
- semantic correctness guarantees from deterministic verification alone.

## Reporting

Security-sensitive findings should be reported privately to the repository owner before public disclosure. Do not include real secrets, credentials, or private repository content in reports.

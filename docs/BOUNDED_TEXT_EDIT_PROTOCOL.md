# Bounded Text Edit Protocol

This document explains the `bounded.controlled-text-edits/v1` contract used by the Controlled Pilot bounded editor.

The normative machine-readable source of truth is:

`scripts/controlled-pilot/text-edit-protocol.cjs`

`TEXT_EDIT_PROTOCOL` defines the protocol version, limits, resolution semantics, materialization order, mutation authority requirements, and invariant text that is serialized into the provider instruction. This document is explanatory; if prose here ever disagrees with the contract object, the contract object is authoritative and the discrepancy is a documentation bug.

## Protocol identity

```text
schemaVersion: bounded.controlled-text-edits/v1
maxEdits: 8
maxTotalUtf8Bytes: 20000
```

## Normative invariants

### Original-source grounded

Every `oldText` refers to the original supplied full source content associated with the edit path. Edits are not sequential authority grants.

An edit produced earlier in the same model response cannot create source evidence for a later edit. Therefore:

```text
original: A
edits:
  A -> B
  B -> C

result: REJECT
```

`B` did not exist in the original supplied source, so the second edit has no valid source span.

### Hash bound

`expectedContentHash` binds the edit to the original supplied source content. It must equal the source file's `contentHash`, and that `contentHash` must itself match the supplied source bytes.

A stale edit hash or a supplied source/hash mismatch is an authority failure, not permission to reinterpret the source.

### Exact unique occurrence

Each `oldText` must occur exactly once in the original supplied full source. Missing and non-unique matches are rejected.

The match is resolved before any replacement is applied.

### Non-overlapping spans

All edit spans for a file are resolved against the same original source snapshot. Two spans may not overlap. A duplicate span is also forbidden, including the same original span with a different replacement.

### Deterministic application

After every edit has passed preflight, replacements for each file are applied in descending original start-offset order.

This order prevents an earlier replacement from shifting offsets needed by another validated original-source span. Materialization order does not change edit authority: all authority and span resolution already happened during preflight.

### No generated-text chaining

Text introduced by `newText` is generated output, not repository evidence. It cannot be used as `oldText` by another edit in the same response unless that text independently existed as a valid exact unique occurrence in the original source.

### Bounded edit count and bytes

A response contains at least one and at most eight edits. The combined UTF-8 byte count of every `oldText` plus `newText` is capped at 20,000 bytes.

### Explicit mutation authority

Every edit must target a required mutation path whose supplied source authority is `change_allowed`. Merely readable, omitted, allowed-but-not-required, or missing source does not grant mutation authority.

## Direct answers for implementers

| Question | Contract answer |
| --- | --- |
| Are edits sequential? | No. They are independently resolved against the same original source snapshot. |
| Is overlap allowed? | No. Overlap and duplicate original spans are rejected. |
| What is `oldText` resolved against? | The original supplied full source identified by the path and `expectedContentHash`, before any edit is applied. |
| What does the hash bind? | `expectedContentHash` binds an edit to the original supplied source content; the supplied source `contentHash` must also match its bytes. |
| Can the same span be edited twice? | No. Duplicate span edits are rejected, even if their replacements differ. |
| Can edit 2 use text generated by edit 1? | No. Generated text does not become authority or evidence inside the same response. |

## Enforcement surfaces

The same contract is preserved through three different surfaces without maintaining three independent prose specifications:

1. `scripts/controlled-pilot/text-edit-protocol.cjs` — normative protocol object and limits.
2. `scripts/controlled-pilot/text-edits.cjs` — provider instruction serialization and deterministic enforcement consume that object.
3. `scripts/controlled-coding-pilot-text-edits-adversarial-smoke.cjs` — regression coverage checks both behavior and serialized instruction invariants.

When changing `bounded.controlled-text-edits/v1`, update the normative contract first. If a change would alter any invariant above, treat it as a protocol compatibility decision rather than a prompt cleanup or materializer refactor.
